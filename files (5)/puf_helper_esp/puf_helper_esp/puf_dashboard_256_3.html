Workflow: enroll once, download the helper data. Download helper data also saves it in the ESP32's flash and replaces any copy already there; for that, connect the WROOM's own USB with button 3 (the DevKit port is receive-only). Later, Load helper data from ESP32 reads it back. For every later session load the helper data instead of enrolling again; a new enrollment forms a new reference and therefore a different key.

Construction. Code-offset fuzzy extractor over one extended BCH code: BCH(255,k,t) plus an overall parity bit gives a (256,k) code, so every one of the 256 PUF bits is protected and nothing is padded. Enrollment: majority-vote the chosen readings into w; encode the k message bits of w to codeword c; publish P = w ⊕ c (only 256−k bits are non-zero); key = HKDF-SHA-256(w, salt, info). Nothing random is drawn, so every enrollment from the same device gives the same stable sequence and the same key (use enough readings that the majority vote is the same each time). Reproduction: XOR a new reading with P, BCH-decode (Berlekamp–Massey + Chien search), re-derive the key and verify it against the stored tag.
Why not pad? Padding with fixed bits adds no PUF information and no protection, so it would only make the sequence look longer. Splitting into 4×BCH(63) leaves 4 bits over and fails whenever any one block has too many errors; one long code is more reliable and gives more secret bits.
Security limit. The key has at most 256−(256−k) = k bits of entropy left after the helper data (less if PUF bits are biased). HKDF cannot add entropy.
